Complementary responsibilities

A shared platform. A verified release. A governed action.

A successful demo proves an agent can help. It does not yet answer who pays, which changes are safe to release, or who authorizes a consequential action. These are different problems — and they need complementary controls.

Data access and privacy remain a separate responsibility. Application and data owners enforce caller/tenant permissions, minimize what enters prompts, memory and audit, and set retention. A private connection or an approved action does not grant access to every record. These controls are not supplied by the new action-governance runtime. Understand the boundary.

01 / Platform and shared services

Many use cases. One accountable AI platform.

Citadel provides a shared foundation for model access, network integration, telemetry and FinOps. Teams keep ownership of their agents without rebuilding these services for every project.

Compatible with an external project, not maintained by Threadlight.
Azure-Samples/ai-hub-gateway-solution-accelerator

Example / shared AI capacity
Three teams share a model pool. An analytics batch consumes the capacity that customer support needs.

Register each use case, set its model and usage policies, and attribute consumption. The platform team can then investigate who used the capacity and make allocation decisions.

A contract, not a shared API key. Citadel connects a business unit, use case and environment to permitted services and usage policies. Model safeguards do not establish business correctness or authorize downstream writes.

Citadel is optional. Threadlight can fit a simpler Foundry-native setup or an existing customer gateway. Network, identity and model controls still need explicit configuration. Deployment options.

02 / AgentOps and release

Deploy through CI/CD — not your laptop.

From development to production, fit the customer's release model: an authorized operator for the pilot, GitHub Actions or Azure DevOps for controlled delivery. Threadlight generates deployment artifacts and runbooks; DevSecOps owns permissions, policy and acceptance. A prompt change still needs evaluation, even when the container starts.

What runs, what you must connect. Provision/deploy and verdict readers are executable. Base evidence-producer steps are echo instructions: wire actual evaluation, red-team and MCP results. The optional AgentOps composition runs a bound evaluation batch, not every producer.

Readers run after deployment. Soft is the default; hard rejects missing or unacceptable verdicts, but evaluation/red-team still accept partial. Readers do not establish freshness or deployment binding. A CI result is not automatic go-live approval.

Fit the customer's delivery controls

--platform

GitHub Actions or Azure DevOps. Configure federated identity, target-scoped permissions and environment reviewers.

--eval-gate / --mcp-gate

Select soft or hard verdict handling. Producing current evidence remains a separate integration step.

--private-network

Select suitable runners; verify DNS, routes and egress. The workload pipeline does not deploy the shared hub.

Evidence before go-live

  1. Inspect configuration

    Review infrastructure, identities, policy and dependencies. Offline checks do not prove a live endpoint works.

  2. Evaluate and red-team

    Run the candidate on representative and adversarial cases, compare with the baseline and apply agreed thresholds. Finding a script is not running it.

  3. Verify the deployed candidate

    Check the actual version, identity and allowed/denied paths with authorized probes. Bind fresh evidence to this deployment; a noop is not business-write proof.

03 / Active governance in production

Access to a system is not authority for every action.

Authentication, network isolation and an approved model do not answer “may this agent change this case, with these facts, now?” Threadlight's runtime references and generators put that decision at the effect boundary: the last controlled point before a selected action changes the business system.

Example / a customer return
“Can I return this order?”
A recommendation is not authorization.

The agent reads the case and proposes an outcome. Eligibility, the current case revision and any required supervisor decision must be checked before recording it.

A decision record, not a payment. This example does not settle a refund.

  1. Read the case

    Retrieve permitted facts and the current revision under the caller's access rules.

  2. Propose the change

    Submit the case, revision and decision. A fabricated approved argument is not authority.

  3. Evaluate policy

    The gateway uses signed rules and trusted facts, not the model's claim of eligibility.

  4. Human decision, if required

    Verify reviewer, role, exact proposal and freshness. Approval authorizes one operation, not an override.

  5. Record authority first

    Consume required approval and obtain central audit ACK before dispatch. Recheck authorization after waits.

  6. Commit and reconcile

    The independent business API checks current state and writes conditionally. Unknown outcome? Reconcile before retrying.

Selected actions, not blanket protection. Opt-in bindings define coverage; invalid selected configuration fails closed. An unbound read remains usable without ACS under its normal access rules. Other tools and deployment paths require their own integration and verification.

The same example, four outcomes

Routine work proceeds. Exceptions stay controlled.

Eligible ordinary return
Policy permits recording the recommendation without unnecessary human review.
High-value case
The supervisor handoff waits for verified human authority.
Outdated case
Changed facts or a conflicting revision block the proposed update.
Repeated completed request
Recheck authority and retrieve the original outcome, not a second business change.
