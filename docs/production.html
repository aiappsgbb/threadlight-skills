Production

From a working pilot to a controlled release.

See what your pilot still needs: an operating foundation, a validated release candidate, and explicit authority for selected business actions. Understand the evidence — and who owns the next decision.

A readiness assessment identifies gaps. It does not certify production.

01 / Starting point

A working pilot is the starting point.

A successful pilot proves that an agent can help. Before it operates real business work, three separate decisions remain — and they belong to different people.

  1. Release

    May this candidate be promoted?

    Owner
    Application team with DevSecOps.
    Decided by
    Required checks bound to the observed candidate, plus environment approval.
    Not the same as
    Go-live: a release result is not automatic go-live approval.

  2. Action authorization

    May this specific change happen now?

    Owner
    Business and policy owners; the runtime enforces.
    Decided by
    Current policy, trusted facts and any required human decision — before each selected effect.
    Not the same as
    A valid release. Release fitness does not grant runtime authority.

  3. Business acceptance

    Do we go live with this residual risk?

    Owner
    Business owner, with security and operations.
    Decided by
    Current evidence, open gaps and explicit, scoped acceptances.
    Not the same as
    An assessment, which informs the decision but does not make it.

02 / Foundation

Choose the foundation you will operate.

The agent itself stays the same: a hosted Foundry agent by default. What you choose is the foundation around it — how model access, network, identity and consumption are controlled.

  • Simplest start

    Foundry with native controls

    No central model gateway yet. Network, identity and model settings are configured for the project; selected actions can still be enforced on the native host path.

  • Brownfield estate

    An existing customer gateway

    An established API Management gateway or network perimeter owned by NetSec. The pilot conforms to it instead of introducing a new hub.

  • Optional shared hub

    Citadel Governance Hub

    One accountable hub for many use cases. Recommended when the customer already runs, or is provisioning, Citadel.

Citadel is optional. Every option still needs explicit network, identity and model configuration. A model gateway governs access to models, not downstream business actions. Compare the three postures.

If many teams share one hub: Citadel.

03 / Validate · AgentOps & release

Validate the candidate before promotion.

Use an authorized operator for a pilot and the customer's controlled pipeline — GitHub Actions or Azure DevOps — for releases. From development to production, Threadlight provides validation and promotion artifacts and runs the required checks; DevSecOps owns integrations, permissions, policy and acceptance. That is AgentOps: a prompt change still needs evaluation, even when the container starts.

Validate a candidate before production. Prepare the proposed version in a separate preproduction environment. Evaluation, adversarial testing and MCP supply-chain checks must pass. A validation record binds results to the observed image, reviewed inputs and current run. Missing, expired or changed evidence stops promotion.

What runs, what you must connect. Threadlight executes the reviewed release sequence and required checks. The application team supplies real deployment, target-observation, evaluation and scanner integrations, plus promotion and recovery behavior. Optional native AgentOps runs a bound evaluation; it does not supply every integration.

A release is one decision. It is not automatic go-live approval and does not authorize runtime business actions. Generator and local native verification are not cloud acceptance; customer-pipeline execution and real business behavior need separately authorized tests.

Evidence before go-live

  1. Inspect configuration

    Review infrastructure, identities, policy and dependencies. Offline checks do not prove a live endpoint works.

  2. Evaluate and red-team

    Run the candidate on representative and adversarial cases, compare with the baseline and apply agreed thresholds. Finding a script is not running it.

  3. Verify the deployed candidate

    Check the actual version, identity and allowed/denied paths with authorized probes. Bind fresh evidence to this deployment; a noop is not business-write proof.

Implementation details: fit the customer's delivery controlsPlatform, acceptance policy and runners
Delivery platform

GitHub Actions or Azure DevOps. Configure separate validation/production identities, scoped permissions and environment reviewers.

Acceptance policy

Review datasets, quality thresholds, attack coverage and evidence lifetime. Required checks cannot become warn-only.

Execution environment

Select suitable runners; verify DNS, routes and egress. The workload pipeline does not deploy the shared hub.

04 / Authorize

Authorize selected actions before they change records.

A validated release does not authorize every action. During operation, selected business changes still need their own policy checks and any required human decision.

The proof is a signed JSON Web Token (JWT)

It binds the verified facts to this caller, case, revision and exact tool arguments. The agent carries it in MCP _meta["threadlight/evidence"]. It is not an access token or human approval.

Current reference: verification uses authenticated HTTPS; the operational call uses MCP.

    05 / Evidence and owners

    Review the evidence. Name the owners.

    Six review questions draw on different evidence. Each has an owner — and a limit on what its proof can show.

    Six review questions, with owner, evidence and limit
    QuestionOwnerEvidenceLimit
    IdentityWho is the agent acting as? Platform and identity team Managed identity and role assignments observed on the deployed candidate Proves who calls, not whether an action is allowed
    Data accessCan it read this record? Application and data owners Caller and tenant permissions enforced at the source; minimization and retention A private connection or approved action does not grant access to every record
    QualityDid the candidate regress? Application team; business owner sets thresholds Evaluation of the observed candidate against the baseline Execution success is not quality success; offline results are not live health
    SafetyCan it be manipulated? Security Adversarial run and MCP supply-chain checks on the candidate Covers the tested attack set only
    Action authorityMay this change happen? Business and policy owners; the gateway enforces Signed policy and enforcement evidence for each selected binding One enforced binding is not whole-agent governance
    Audit & telemetryWhat happened, when, for whom? Operations Central audit acknowledgement before the effect; traces and alerts A local spool is not hosted audit proof

    Five kinds of proof. Each shows something different.

    1. Generated artifact

      Shows: configuration and wiring exist.

      Not: that anything ran.

    2. Offline inventory

      Shows: declared policy and bindings.

      Not: enforcement.

    3. Executed LOCAL-14

      Shows: selected paths behave locally.

      Not: hosted behavior.

    4. Native/CTK

      Shows: native contract conformance on this host.

      Not: Azure or customer behavior.

    5. Live evidence

      Shows: fresh observations bound to this deployment.

      Not: anything beyond what was observed.

    Fresh, not inherited. The deployed collector proves only governance_probe_noop, not business writes. A new deployment needs fresh evidence; historical records are not inherited by this page or by new deployments.

    Per binding, not per agent. One enforced binding is not whole-agent governance. Unbound reads stay usable without ACS; accepting a consequential unbound action must be explicit, current and scoped.

    Data access and privacy remain a separate responsibility. Application and data owners enforce caller/tenant permissions, minimize what enters prompts, memory and audit, and set retention. These controls are not supplied by the new action-governance runtime. Understand the boundary.
