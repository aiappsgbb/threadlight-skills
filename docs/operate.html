Operate a governed agent after go-live

A release is a starting point. These five routines keep the evidence current, stop unsafe changes and turn surprises into tests. Each one is a request you give your coding agent, with the result to expect and the check to make.

Guided requests: this is guidance, not cloud execution. Next never runs Azure or marks a check as passed.

Cloud · approved read-only scope

After every deployment, collect fresh evidence

Prove that what runs now is what was accepted: same image, identities, binding and policy. Old receipts do not carry over.

Skills threadlight-safe-check threadlight-production-ready

Prompt

Run threadlight-safe-check --phase post-deploy against the environment I just deployed, within the read-only scope I approved.
Confirm every deployed image is the accepted immutable image, the identities and roles match the manifest, and each channel is reachable.
If the governance collector is configured, record its governance_probe_noop result as runtime-path evidence only, not as proof of a business write.
Then run threadlight-production-ready to rescore the pillars with this fresh after-deployment evidence. Do not reuse candidate or earlier receipts.
List the remaining gaps with an owner for each. Do not remediate, redeploy or change configuration.

Expected result

Read-only; evidence is dated and tied to this deployment.

  • Post-deploy gaps (empty means complete)
  • Rescored readiness with named owners
Evidence freshness rules

Verify

  • The evidence names the same image, environment, identities and policy bundle that were approved; anything older than its freshness window is marked stale, not green.
  • governance_probe_noop is reported as a runtime-path probe only. Business writes still need their own binding evidence.
  • No configuration, role or resource changed during collection.
Candidate · explicit approval · budget

Before any change, gate it like a release

A new prompt, model, tool or policy is a new candidate. Compare it with the champion before it reaches users.

Skills threadlight-evals threadlight-redteam threadlight-cicd

Prompt

I want to change [prompt / model / tool / policy]. Treat it as a new release candidate.
Use threadlight-evals to run a champion-challenger comparison on the existing dataset and regression cases; report any metric that drops below its threshold.
Use threadlight-redteam for the attack categories this change touches. Paid or cloud runs need my approval and a stated budget first.
Prepare the change through threadlight-cicd's verified-release contract: build one immutable image, attach the eval and red-team receipts, and stop if any required check is missing or expired.
Do not promote. Show me the comparison and the candidate receipt for approval.

Expected result

A candidate awaiting approval; production unchanged.

  • Champion versus challenger scores
  • Candidate receipt for one image
Verified-release contract

Verify

  • Promotion later uses the same immutable image the checks ran against; nothing is rebuilt from a mutable tag.
  • A missing, failed or expired check stops the candidate instead of being waived silently.
  • Policy or binding changes carry a new signed policy bundle, not an edited copy of the old one.
Scheduled review · read-only

Every week, review cost, drift and stale evidence

Catch slow problems early: spend that departs from the forecast, preview features nearing expiry, evidence that has quietly aged out.

Skills threadlight-consumption-iq threadlight-upgrade threadlight-agentops

Prompt

Run my weekly operations review. Everything is read-only.
Use threadlight-consumption-iq to collect actuals for the approved scope and reconcile them with the forecast; flag any line more than the agreed tolerance away.
Use threadlight-upgrade in plan-only mode to list dependency staleness and preview features approaching expiry, with one ordered migration plan.
If this repository has opted in to AgentOps, run threadlight-agentops with --freshness-hours 168 and list each stale or missing evidence item.
Summarize as: cost variance, drift, stale evidence, and who owns each follow-up. Do not upgrade, resize or delete anything.

Expected result

A short review; no resources changed.

  • Actuals against forecast
  • Migration plan and stale-evidence list
Agent operations reference

Verify

  • Each finding has an owner and a date; a variance or drift item without an owner is not closed.
  • Upgrades from the plan go through routine 2 as a new candidate, never straight to production.
Incident · named owner

When an outcome is unknown, stop and reconcile

A timeout or lost runner does not mean nothing happened. Find out what actually changed before anyone tries again.

Skills threadlight-cicd threadlight-governed-actions

Prompt

A [promotion / governed action] ended with an unknown outcome. Help me reconcile it without retrying.
Keep traffic closed. Using threadlight-cicd's release contract, read the durable operation record for this operation_id and independently read back the actual target: image, revision and routing.
For governed actions, use threadlight-governed-actions to check the audit trail: was the approval consumed, was the effect acknowledged, is there any duplicate?
Report what is known, what is still unknown, and the options for the incident owner. Do not retry, roll back, delete or clean up anything.

Expected result

A reconciliation report; the decision stays with the owner.

  • Observed target versus intended target
  • Audit and approval status
Failure and reconciliation rules

Verify

  • Routing stays closed until the owner accepts the reconciled state. A red CI run is not proof that no effect happened.
  • No automatic rollback: rollback, retry and cleanup each need their own authorization from the incident owner.
Offline · reviewed change

Learn from what happened, then test for it

Every surprise should become a check that would have caught it. Improvement goes through review, never self-modification.

Skills threadlight-router-bench threadlight-evals

Prompt

Use threadlight-router-bench learn [run_id] on the CI run from this incident or release, and summarize the grounded learnings.
For each exception the agent missed or mishandled, draft a regression case for the threadlight-evals dataset with the expected behaviour.
Propose any prompt, tool or policy change as a pull request for review. Do not edit the running agent or merge anything.

Expected result

Offline; proposals only.

  • Learnings digest from the run
  • New regression cases and a reviewable pull request
How the improvement loop works

Verify

  • The new regression case fails on the old behaviour and passes on the proposed change.
  • The change returns to routine 2 as a candidate; a reviewer, not the agent, approves it.
