threadlight-customize is a manual production-handoff runbook. Keep skills untouched, put customer inputs in an overlay, then verify identity, network and release boundaries with their platform team.

No automatic onboarding or production approval. The overlay supplies inputs; it does not prove that customer controls work. Open the handoff runbook ↓

Same skills, same code — only the inputs change. That is the whole point.

01A public pilot cannot prove a private estate.

Defaults are a starting position, not a mandate. Keep what fits; override inputs where customer policy differs. This is instructions, not a generator — customer-specific branching does not belong in the skills.

  • Identity → scoped pipelineCustomer OIDC / WIF, spoke-RG RBAC and approved runners go into overlay/cicd/.
  • Network → reachable endpointsResolve private DNS and reach port 443 from inside the perimeter before deployment.
  • Ownership → signed boundaryRecord exclusions in non-coverage.md. An architecture review, not a generated score, accepts the handoff.

02Four seams. No edited skills.

Capture keep-vs-override decisions with the platform owner. Every customer input stays beside the pinned fork.

Testing inside their boundary

A private-VNet target needs a dev box inside the perimeter. Three patterns, one gate.

L300 · Compare in-VNet development, Codespaces and cloud sandboxes
DimensionAzure ML compute + VS Code strongGitHub CodespacesGitHub cloud sandbox
NetworkJoined to the VNet, no public IPPublic-egress by default; needs a sanctioned path or enterprise Azure private networkingPublic-egress, GitHub-hosted; traffic bounded by your org’s Copilot cloud-agent policy
Private endpointsReaches Foundry / ACR / Cosmos / Key Vault nativelyOnly via a sanctioned tunnel or enterprise private networkingSame as a vanilla Codespace — no line of sight to private endpoints
Best forFully-private, no-egress targetsFast iteration on the non-private parts of the loopZero-install, throwaway runs from any machine — the design / local-test legs
Honest limitSingle-user box; stop it when idle to control costA vanilla Codespace can’t see private endpointsPublic preview & usage-billed; no az / azd or subscription creds preloaded

Either way the gate is the private-VNet pre-flight: private DNS resolves to private IPs, 443 reaches every private endpoint, and control-plane egress is allowed — only then deploy. A half-resolved DNS zone fails the deploy looking like an auth error and burns an afternoon; the checklist catches it first. Pre-flight checklist ↗

03Take the handoff to review.

Start intake during the pilot. Missing customer inputs block the handoff; a generated score cannot accept the boundary.

L300 · Fork commands, handoff steps and one real override 
# 1 · fork into the customer org and clone (gh wires origin + upstream)
> gh repo fork aiappsgbb/threadlight-skills --org <customer-org> --clone --remote
> cd threadlight-skills

# 2 · pin the exact upstream commit you forked from
> git rev-parse upstream/main   # → record this SHA in overlay/upstream-pin.md

# 3 · scaffold the overlay — customer inputs live here, never in skill files
> mkdir -p overlay/{deploy,production-ready,cicd,safe-check} docs/threadlight-customize
  1. Intake — the long pole. Fill customer-profile.md with their platform owner: documents, environment setup, requirements, mandated template / starter code. Every blank is a blocker.
  2. Fork & pin. Fork into the customer org; record the SHA in overlay/upstream-pin.md (commands above).
  3. Scaffold the overlay. One mkdir -p stands up the four skill folders plus the engagement-record directory.
  4. Map keep-vs-override. Fill customization-map.md — name the exact selector, azd env, or threshold to change per skill. Map template ↗
  5. Drop real overrides. Put the customer’s values in overlay/ — for example the customer-overrides.yaml below. Never edit a skill file.
  6. Test inside the boundary. Pre-flight green, then run the local-test / deploy loop on the in-VNet box.
  7. Name the boundary. Record what you customized and what Threadlight deliberately doesn’t automate in non-coverage.md — the architecture review signs off on this.
  8. Pull upstream later. Review git merge upstream/main, re-test the overlay and re-pin the new SHA. Full runbook ↗

One real override

# overlay/production-ready/customer-overrides.yaml
customer: <customer-name>
overrides:
  - recipe_id: SEC-105            # should-fix: KV access via RBAC, not legacy policies
    status: pass                  # customer uses an approved equivalent control
    reason: "Governed by the customer's audited PIM workflow; reviewed 2026-Q2."
  - recipe_id: NET-103            # should-fix: NSG flow logs on spoke subnets
    status: fail                  # customer is STRICTER than our default
    reason: "Customer audit policy mandates flow logs on every spoke subnet."

Overrides are status flips only (pass ↔ fail) on should-fix findings, each with a written reason for the audit trail. A must-fix finding cannot be flipped — the scorecard exits non-zero and names it. The decision lives in the overlay, never in an edited skill.
