Offline · read-only

Inspect the pilot you already generated

Identify its current runtime, tool boundaries and evidence gaps without rebuilding it.

Skills threadlight-governed-actions Inventory only

Prompt

Use the inventory rules from threadlight-governed-actions to inspect my existing Threadlight pilot read-only.
Read specs/SPEC.md, specs/foundation.md, specs/manifest.json, registered tools, identity mappings and retained generated artifacts/evidence.
Do not run probes, emit files, remediate, regenerate the SPEC or switch the runtime.
Summarize the current supported profile, read versus consequential tools, existing bindings and missing evidence. No Azure discovery or rights probes.

Expected result

Read-only; no files emitted.

  • Inventory summary
  • Evidence gaps
Inventory check details

Verify

  • The inspected repository and existing foundation/manifest agree on runtime, protocol and tools.
  • The inventory distinguishes declared, locally tested and deployment-verified paths; original files remain unchanged.
Offline · owner review

Select the missing action controls

Review only the delta: protected actions, identities, human channel and target posture.

Skills threadlight-govern

Prompt

Use threadlight-govern to propose the governance delta for the existing SPEC, foundation and tool inventory.
Select named protected actions in specs/governance-contract.json; preserve authenticated unbound reads.
Match the current runtime to a supported human channel. Deferred Outlook resume requires the supported MAF/gateway profile; report incompatibility instead of silently switching frameworks.
Reuse the approved target posture and identity owners. List required trusted facts, exact role/resource/expected-identity assignments and human consent handoffs. Do not force private conversion or assume administrator rights.

Expected result

A proposal for owner review.

  • Governance delta proposal
  • Reviewed selection for specs/governance-contract.json
Policy and binding details

Verify

  • The reviewed contract names actual existing tools, backend targets/facts and a supported runtime/channel combination.
  • The owner has approved the target/posture and permission delta; personal consent is still a real human handoff.

Requesting-user confirmation is separate from reviewer approval. Select the native Logic Apps/Outlook provider and MAF gateway path explicitly. The original requesting user selects Approve or Reject; email is not MFA. Scoped live proof; new deployments remain unverified.

Offline preparation · platform handoff

Prepare the governed release candidate

Reuse generated sources and prepare the missing integrations, not another pilot or pipeline.

Skills threadlight-deploy threadlight-cicd

Prompt

Use threadlight-deploy and threadlight-cicd with the reviewed delta and existing generated host, tools, infrastructure and CI.
Prepare only missing governance integrations and the current verified-release candidate plan. Do not overwrite unrelated generated artifacts or existing workflows.
Identify real application-owned prepare/observe/eval/red-team/promote adapters and configure the reviewed specs/release-policy.json.
Hand off exact permission assignments, publisher authority, native identity observation and fresh binding to the platform owner. Stop for missing prerequisites; do not deploy, grant permissions or manufacture signed evidence during preparation.

Expected result

No image build or deployment in this preparation step.

  • Reviewed candidate inputs
  • specs/release-policy.json
  • Adapter handoff
Release preparation details

Verify

  • The candidate plan reuses current sources; real adapters, datasets, thresholds and immutable-image provenance are reviewed.
  • Validation/production identities and protected approvals are separate; the publisher and observed-identity binding handoffs are explicit.
Cloud · explicit approval · real reviewer

Execute the approved candidate checks

Produce fresh candidate evidence, including the selected business action and human review.

Skills threadlight-cicd threadlight-governed-actions threadlight-safe-check Each within its documented scope

Prompt

Only after I separately approve the exact existing target, model, change list, scoped permissions and test budget, use threadlight-cicd's reviewed candidate workflow/adapters.
Observe the actual candidate version/image/identity and current signed binding. Run configured real eval, red-team and MCP producers.
Use threadlight-governed-actions and threadlight-safe-check for their documented scopes; governance_probe_noop is not business-write proof.
With a real authorized reviewer, verify supported allow/deny/pending, exact same-session human resume, replay and independently joined business/audit records. No borrowed reports, fabricated consent or automatic retry of unknown outcomes.

Expected result

Only after accepted execution, not by clicking Next.

  • Accepted validation receipt: .threadlight-release/candidate.json
  • Business/audit correlation
Human review and audit details

Verify

  • Fresh evidence joins the observed candidate and selected binding; allow/deny/human/audit outcomes come from actual execution, not model prose.
  • Required eval/red-team/MCP gates pass; .threadlight-release/candidate.json exists only after accepted validation.
  • The reviewer and original session/arguments match; replay creates no second business effect.
Cloud · production approval · operations

Approve promotion and observe production

Promote the same tested image, verify the actual target and complete the operations handoff.

Skills threadlight-cicd threadlight-production-ready

Prompt

Use threadlight-cicd's existing verified-release contract after protected production-environment approval.
Recheck the current candidate receipt and promote the same immutable image; do not rebuild it or borrow candidate evidence as production proof.
Independently observe production and obtain the required fresh production binding/business evidence. Keep routing closed until application-owned acceptance is complete.
Use threadlight-production-ready for the current gaps and operations handoff. Name incident, identity/key/reviewer, budget and retention owners.
Reconcile unknown outcomes through the existing main contract, not an unmerged operator API. Retain sanitized evidence; cleanup is separately approved and limited to new test-owned temporaries, never shared/demo environments.

Expected result

Only after the approved run and independent readback.

  • Production observation
  • Operations handoff with remaining gaps
Release and operations details

Verify

  • Production observation matches the accepted immutable image and current authority; release approval is not action approval or business go-live.
  • The operations owner has the remaining gaps, retained evidence and exact test-owned cleanup scope. No automatic rollback or deletion is implied.
