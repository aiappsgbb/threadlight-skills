## Target file

Retain the actual drill in `docs/restore-drill*.md|json`,
`docs/restore-drills/*.md|json`, `tests/restore-drill*.md|json` or
`evidence/**/restore-drill*.*`. Do not fabricate a new report to clear the finding.
Existing Markdown reports can add the labels below from their original records.
Filename dates and filesystem **mtime never establish execution or freshness**.

## Edit type

`manual`: assessment never performs a restore. Use `azure-backup-readiness` and
the service-specific approved restore runbook. Azure Quick Review inventories
configuration; it is not a restore-drill executor.

## Edit recipe

Before live work, approve the exact source, restore point, isolated target,
budget and cleanup inventory. Do not restore over the source or delete retained
demo/customer data. Restore the application's consistent recovery set, including
business, approval, audit and idempotency state where applicable; a database-only
smoke does not prove application recovery.

Collect the real restore job output and independent data-integrity/application
checks. Preserve sanitized raw evidence and its SHA-256 before targeted cleanup.
Record these fields as JSON keys or Markdown labels (`**Completed at:** ...`;
spaces map to underscores):

| Field | Required fact |
|---|---|
| `completed_at` | Actual timezone-aware execution time; not future, at most 90 days old |
| `subscription_id`, `resource_group` | Exact assessed source environment |
| `drill_owner` | Responsible operator, not a placeholder |
| `protected_item` | Full source resource ID within the assessed environment |
| `restore_point_selected` | Actual recovery point or immutable backup identifier |
| `restore_target` | Full isolated restored resource ID, distinct from source |
| `result`, `validation` | Both exactly `success`, only after restore and data/application checks succeed |
| `rto_seconds`, `rpo_seconds` | Measured nonnegative numbers; compare separately with declared targets |
| `evidence_ref`, `evidence_sha256` | Root-relative retained raw job/verification evidence file and its exact SHA-256 |

No date fallback exists. Stale, future, failed, malformed or unfilled reports
remain `not-verified`; absent evidence is `must-fix`. The newest **valid execution**
is used, not the newest file. Historical short-form documents still describe
what was recorded, but cannot prove missing target/outcome/measurement facts.
A passing finding verifies retained drill evidence, not a new live execution or
that measured RTO/RPO met a customer's targets.

## Verification

or incomplete drills stay visible; document accepted risk only through the
existing `tests/production-readiness-waivers.json` contract, with explicit
