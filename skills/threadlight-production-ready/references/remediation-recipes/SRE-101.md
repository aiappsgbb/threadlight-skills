## Target file

`docs/alert-routing.json` identifies the intended on-call route. Infrastructure
changes remain in the application's existing observability module.

## Edit type

`replace`: prepare reviewed configuration only. Deployment and test notifications
need explicit approval; assessment is read-only.

## Edit recipe

Use the [Azure Monitor action-group contract](https://learn.microsoft.com/azure/azure-monitor/alerts/action-groups)
and `azure-monitor-alert-baseline` or `foundry-observability`. Receivers belong
directly to properties such as `emailReceivers` or `webhookReceivers`, not a
generic `receivers` array. Do not invent a Teams receiver type or embed webhook
secrets. The platform owner configures the supported connector/channel.

Record exactly these JSON fields from the approved configuration:

| Field | Meaning |
|---|---|
| `action_group_id` | Full expected action group resource ID |
| `rule_id` | Full metric, activity-log or scheduled-query alert rule resource ID |
| `target_resource_id` | Exact resource in that rule's `scopes` |
| `receiver_type` | Supported receiver collection, e.g. `emailReceivers` |
| `receiver_name` | Exact configured receiver name |
| `destination_sha256` | SHA-256 of the exact configured destination UTF-8 bytes; do not publish addresses, URLs or secrets |

All three resource IDs must be in the assessed resource group/subscription for
this bounded check. Shared cross-RG routing and unsupported receiver types remain
`not-verified`, not automatically broken. The assessor checks group/rule
`enabled`, rule target and action-group mapping, and the named receiver's
destination. Disabled/missing/mismatched configuration cannot pass.

**Configured is not delivered.** An enabled route remains `not-verified` until
an explicitly authorized, bounded test yields a real **correlation** receipt.
Preserve it at `evidence/alert-delivery.json`, containing the same six routing
fields plus `status: "delivered"`, `test_started_at`, `received_at`,
`correlation_id`, `evidence_ref` and `evidence_sha256`. Both timestamps must
be timezone-aware, non-future and within 24 hours; receipt time cannot precede
test start. The root-relative evidence file must contain retained sanitized
receiver/delivery evidence with matching SHA-256. A send-request ACK or the
existence of an action group is not delivery evidence. The evidence owner is
responsible for independent receiver provenance, not a model's assertion.
The supported retained receiver event is JSON with `id` matching the receipt's
`correlation_id`, `status: "delivered"`, exact `actionGroupId`, `receiver` name
and matching `received_at`. These are independently exported receiver facts,
not fields to populate from a send-request ACK. An unrelated or stale raw event
cannot validate a newly dated summary. Other export shapes stay not-verified
until a reviewed producer supplies this mapping; do not fabricate an event.
