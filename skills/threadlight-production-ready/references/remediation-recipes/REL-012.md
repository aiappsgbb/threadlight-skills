## Target file
`src/agent/container.py` and any tool that writes outside the agent.

## Edit type
`invoke-sibling`

## Edit recipe
1. Recovery re-enters the handler from the top and re-runs the interrupted
   phase ([Learn: resilience concept](https://learn.microsoft.com/azure/foundry/agents/concepts/long-running-agent-resilience)).
2. Governed gateway calls: wrap each phase in `maf_gateway.recovery_scope(context.response_id, phase)`
   (the long-running template's `effect_scope` does it), so a re-run reuses the
   operation id; see `threadlight-governed-actions` § Recovered handlers.
3. Other effects: pass an idempotency key derived from the response id, phase and
   action, or set a watermark before dispatch and clear it after commit. An
   unknown outcome stays UNKNOWN until reconciled; never replay it.

## Verification
Re-run threadlight: `python3 skills/threadlight-production-ready/scripts/production_ready.py --root <project>`. REL-012 flips to `pass` when an idempotency key, `recovery_scope` / `effect_scope` or a watermark fences the effects. This is inventory, not proof that every effect is fenced.
