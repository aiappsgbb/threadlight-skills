## Target file

`skills/threadlight-consumption-iq/references/pricing-fixtures/meters.json`
(dated meter rates) and/or `specs/SPEC.md` § 12 (declared monthly volumes).
`specs/cost-manifest.json` is regenerated by `threadlight-consumption-iq`.

## Edit type

`replace` — add or update a dated fixture rate, or fill in a missing SPEC § 12
volume. No infrastructure change is required to close the coverage gap.

## What COST-007 checks

`COST-007` reads the vNext meter-coverage surface of `specs/cost-manifest.json`
(produced by `threadlight-consumption-iq`'s `cost_api.project_profile`). Every
detected billable line carries a `pricing_status`, and the manifest carries a
`meter_coverage.status`:

| Condition | Status emitted |
|---|---|
| Any detected resource/meter line has `pricing_status: not-priceable` | `must-fix` |
| No not-priceable line, but `meter_coverage.status: not-verified` | `not-verified` |
| `meter_coverage.status: complete` and every line priced | `pass` |

When the manifest has no `meter_coverage` key (a v1 manifest), `COST-007` is
`not-verified` — the vNext projection has not been run yet. This never changes
`COST-005`/`COST-006` outcomes.

## Edit recipe

1. **Open `docs/cost-projection.md` / `specs/cost-manifest.json`** and find the
   lines flagged `not-priceable` (no retail rate) and the meters flagged
   `not-verified` (no declared volume).

2. **For each `not-priceable` line**, add a dated rate to the meter fixture
   (`references/pricing-fixtures/meters.json`) — keep `_last_refreshed` current
   and cite the source — or, if the meter has no projector at all, register one
   under `skills/threadlight-consumption-iq/scripts/projectors/`. Never invent a
   rate: if a public retail price genuinely does not exist yet, leave it
   not-priceable and record a waiver.

3. **For each `not-verified` meter**, declare the missing monthly volume in
   SPEC § 12 (for example `pages_per_month`, `media_hours_per_month`,
   `retrievals_per_month` + fan-out) so the projector can compute a cost.

4. **Re-run `threadlight-consumption-iq`** to regenerate the manifest:
   ```
   python3 skills/threadlight-consumption-iq/scripts/consumption_iq.py estimate --from-profile specs/cost-profile.json
   ```

5. **Re-run `threadlight-production-ready`** and confirm `COST-007` flips to
   `pass`:
   ```
   python3 scripts/production_ready.py --target-rg <RG> --target-sub <SUB> --static
   ```

## Why this is `kind: manual` and not auto-applied

Adding a retail rate requires a human to confirm the meter, region and source
of the price; declaring a monthly volume is a customer-supplied planning input.
Both are judgment calls that must not be guessed by an automated patch — an
invented rate would present a falsely complete bill.

## Verification

After completing the steps above, re-run the assessor and confirm:
- `COST-007` status is `pass`
- `specs/cost-manifest.json → meter_coverage.status` is `complete`
- no line in `resources[]` / `meters[]` has `pricing_status: not-priceable`

## Stale-plan check (the agent MUST do this before applying)

Recompute `sha256(canonical_json(<current production-readiness-manifest.json>))` and compare against `apply_plan["manifest_sha256"]`. If they differ, the plan is stale — refuse to apply and ask the operator to re-run `--onboard` to get a fresh apply-plan. See SKILL.md "Stale-plan detection" for the full contract.
