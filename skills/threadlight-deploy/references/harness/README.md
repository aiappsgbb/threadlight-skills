# Foundry Copilot harness route (generate_only, preview)

Generated by `scripts/generate_only.py` only when SPEC § 11e resolves to
`agent_type: harness` (the user's preview opt-in, a complete `harness_fit`
record, no disqualifier; `skills/_shared/foundry-only-agents.md` item 2d).
Code: [`scripts/harness_route.py`](../../scripts/harness_route.py). Official
source: [Use the Microsoft Copilot harness with prompt agents](https://learn.microsoft.com/azure/foundry/agents/how-to/use-tools-skills-copilot-harness).

## What the project contains

| Piece | Shape | Why |
| --- | --- | --- |
| Agent | `host: azure.ai.agent`, `kind: prompt`, `harness.type: microsoft_copilot_preview`, `model`, inline `instructions` from `AGENTS.md`, `project: src/agent` | Foundry runs the loop; no agent container. `project` anchors `skills/` (below). |
| Skills | one `host: azure.ai.skill` service per `src/agent/skills/<name>`, `archive:` the folder, listed in the agent `uses` and `skills` | `azd deploy --all` publishes each skill and pins its immutable version in the agent. |
| Harness tools | one `microsoft_copilot_toolset_preview` block, `defaultConfig.enabled: false`, only `filesystem_read` on | Shell and web stay off unless SPEC § 11e `harness_toolset` names them. Shell is not a strict boundary (Learn). |
| SPEC tools | one `mcp` tool on the mock MCP server; reads in `require_approval.never.tool_names`, every write needs approval | The client answers `mcp_approval_request`. |
| Egress | `infra/harness-egress.bicep`: RAI policy, `egressPolicy` default Deny, **Audit** first; attached as `policies: [{type: rai_policy}]` | Telemetry and Agent 365 hosts are always allowed. |
| Hooks | `preflight.sh` (preprovision, postprovision, predeploy), `postdeploy.sh` | Preview flag check; Foundry User on the project for the agent identity. |

Not available on this route: `--profile private`, SPEC 11a governance and
`consequential_write_seam: function-tool` (separate routes), the hosted
voice front-end, and harness evals (the generated `evals/run_evals.py` still
sends the hosted Invocations body).

## SPEC § 11e fields

```yaml
harness_toolset: filesystem_read          # comma list of filesystem_read, filesystem_write, shell, web, subagents
harness_egress_allow: null                # extra hosts the sandbox may reach directly, e.g. learn.microsoft.com
harness_egress_mode: Audit                # Audit | Enforced (switch later with THREADLIGHT_HARNESS_EGRESS_MODE)
```

## Findings this route encodes

- **[Tested, 2026-11-21]** `azure.ai.agents` 1.2.0 resolves a local skill's
  published version from `<agent service project>/skills/<name>`. Without
  `project:` the shorthand `skills: [name]` failed with "prompt skill requires a
  version", and `version: ${SKILL_<NAME>_VERSION}` is sent literally (not
  substituted). With `project: src/agent`, `azd deploy --all` pinned the skill.
- **[Tested, 2026-11-21]** Learn shows `require_approval: {"never": [...]}`; the
  service rejected it ("Expected object, got Array") and accepted
  `{"never": {"tool_names": [...]}}`.
- **[Tested, 2026-11-21]** The egress RAI policy and the project creation raced
  on the account (`RequestConflict`); the module now depends on project and model.
- **[Tested, Nov 2026, #229]** An `input_file` passed by Foundry **file ID** was
  silently skipped until the agent identity had Foundry User on the project
  (Learn lists that role for Toolbox calls and returned files).
- **[Tested, Nov 2026, #229]** With egress Enforced and only customer hosts
  allowed, the agent emitted no agent spans; allowing
  `*.in.applicationinsights.azure.com`, `*.livediagnostics.monitor.azure.com`,
  `settings.sdk.monitor.azure.com` and `agent365.svc.cloud.microsoft` restored
  tracing. Learn says Foundry preserves the platform connectivity the harness
  needs; it does not list these hosts.
- **[Documented]** azd ≥ 1.37.0, `azure.ai.agents` ≥ 1.0.0-beta.22 and
  `AZD_ALPHA_ENABLE_AGENTS_MANAGED_HARNESS=true` in every shell and CI job.
- **[Tested]** A model 429 fails the whole harness response: size TPM at
  concurrent conversations x ~300K tokens (`threadlight-qualify`).

## Governance claims

ACS and Agent Hooks do not run inside the harness, so the hosted runtime's
LOCAL-14/CTK evidence does not apply. On this route a write is gated only by
the MCP approval round trip that the client answers. Governed writes through
client function tools and the governed gateway are documented, with the
claims that apply and do not apply, in
[`threadlight-govern/references/harness/README.md`](../../../threadlight-govern/references/harness/README.md).
