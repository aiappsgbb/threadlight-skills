# Private profile: the same pilot, promoted to a private network

`generate_only.py --profile private [--model-gateway apim]` re-packages a
Threadlight design workspace, or an already generated Fast-PoC (with
`--force`), for a private network. Design files (`AGENTS.md`, `specs/`,
`src/mcp/server.py`), the agent runtime (`src/agent/`), the MCP server packaging
and the evals stay **byte-identical** to a Fast-PoC generated by the same
catalog version. Only `infra/`, `azure.yaml` (one agent variable and two hooks),
the private hooks, `scripts/private/vnet_run.py`, the posture, the deferred
steps and `DEPLOY.md` change.

Canonical sources: `references/hosted-agent/ghcp/references/pilot/infra-private/`
(adapted from the official
[11-private-network-basic-vnet](https://github.com/microsoft-foundry/foundry-samples/tree/main/infrastructure/infrastructure-setup-bicep/11-private-network-basic-vnet)
template, commit `2c5eac99`) and `references/generate-only/templates/vnet_run.py.tmpl`.

## What is private, and how

| Piece | Fast-PoC | Private profile | Source |
|---|---|---|---|
| Foundry account | public | `publicNetworkAccess: Disabled`, private endpoint, hosted-agent VNet injection on first create | [Agent Service private networking](https://learn.microsoft.com/azure/foundry/agents/how-to/virtual-networks) |
| Hosted agent egress | platform | delegated `snet-agent` (/24) through a NAT gateway | [networking deep dive](https://learn.microsoft.com/azure/foundry/agents/concepts/agents-networking-deep-dive) |
| Container registry | Basic, public | Premium, private endpoint; public endpoint Deny-by-default, only the region's `AzureContainerRegistry` service-tag prefixes (ACR Tasks) | [ACR private endpoints](https://learn.microsoft.com/azure/container-registry/container-registry-private-endpoints) |
| MCP server | public Container App | internal Container Apps environment, private DNS zone for its domain | — |
| App Insights | public ingestion | ingestion only through an Azure Monitor Private Link Scope | same Learn page, "What VNet protection means" |
| Model route | project endpoint | project private endpoint, or API Management Standard v2 (private endpoint in, VNet integration out, public access disabled) | [APIM VNet options](https://learn.microsoft.com/azure/api-management/virtual-network-concepts) |
| Evaluations | — | project identity has Foundry User on the account; project capability host | [evaluation in a VNet](https://learn.microsoft.com/azure/foundry/concepts/evaluation-virtual-network) |
| Operator | laptop | laptop provisions; an in-VNet VM (no public IP) deploys, invokes and evaluates through Run Command; Bastion Developer for people | [Run Command limits](https://learn.microsoft.com/azure/virtual-machines/linux/run-command#restrictions), [Bastion SKUs](https://learn.microsoft.com/azure/bastion/bastion-sku-comparison) |

`threadlight-safe-check --phase post-deploy` reads `networking: private` from
`specs/deployment-posture.md` and checks every resource in the group from the
control plane: public network access off (or the ACR exception above), approved
private endpoints, DNS zone groups whose zones are linked to a VNet, App
Insights ingestion disabled, internal Container Apps environment, agent network
injection. Key Vault, Storage, AI Search and Cosmos DB are checked the same way
when a pilot adds them (the base GHCP pilot creates none).

## Why these choices

- **Region.** The Foundry account must be in the VNet's region. East US 2 is the
  default in `DEPLOY.md` because Bastion Developer is offered there and not in
  West US 3.
- **ACR.** `azd` remote builds run as ACR quick builds. They fail on a registry
  with public network access Disabled (observed 2026-11-11: `denied: client with
  IP ... is not allowed access`), even with trusted services and
  `networkRuleBypassAllowedForTasks`, because quick builds need a dedicated agent
  pool (preview) and `azd` sends no agent pool in its build request. Allowing
  only the regional ACR Tasks prefixes made the same build pass while the laptop
  stayed denied. `THREADLIGHT_ACR_BUILD_ACCESS=none` disables the public endpoint
  for teams that build inside the network.
- **Gateway tier.** Standard v2 is the lowest tier with both an inbound private
  endpoint and outbound VNet integration; Developer (classic, internal VNet
  injection) is cheaper but needs subnet NSG rules and long provisioning and has
  no SLA (not proven here). Standard v2 is a recurring charge: delete it after a
  test if the pilot doesn't need it.
- **Gateway URL.** `MODEL_GATEWAY_URL` ends in `/openai/v1`. With
  `ProviderConfig(type="azure")`, github-copilot-sdk 1.0.1 keeps only the origin
  of any other base URL (it posted to `/openai/v1/responses` without the
  `/models` prefix; APIM answered 404). Observed live and with a local probe.
- **Non-Azure gateway.** Same pattern: a pass-through route to the project
  endpoint that serves streaming `/openai/v1/responses` with a Microsoft Entra
  token for `https://ai.azure.com`. Not generated or proven. Foundry's own
  bring-your-own-model connections are documented as not supported with the
  Microsoft Copilot harness ([BYOM](https://learn.microsoft.com/azure/foundry/agents/how-to/ai-gateway));
  this pilot runs the GitHub Copilot SDK in its own container and routes its own
  model calls, so it doesn't depend on that feature.
- **Operator host.** With public access off, Foundry data-plane calls (create
  the agent version, invoke, evaluate) work only from inside the network. A
  small VM with no public IP, driven from the laptop through Run Command, is the
  cheapest honest path; CI should use a self-hosted runner in the VNet. The VM's
  identity has Contributor on the resource group, Foundry User on the account and
  a role-assignment right limited by condition to Foundry User, AcrPull and
  Container Registry Repository Reader.

## Run order

1. Laptop: `azd provision` (control plane). Hooks set the ACR prefixes, the
   operator key, and the App Insights and registry project connections.
2. Laptop: `python scripts/private/vnet_run.py sync`, then
   `run "azd deploy --no-prompt"`, invoke, `record_deploy_evidence.py`,
   `run_evals.py`, `get specs/foundry-package-manifest.json`.
   Sync **after** each `azd provision` and **before** `azd deploy`: the host
   keeps its own azd environment values from deploy until the next sync.
3. Laptop: `safe_check.py --phase post-deploy`.

## Live record (2026-11-11, internal nonproduction subscription, East US 2)

The 2026-11-09 returns-triage recommend-only Fast-PoC was copied unchanged and
promoted with `--profile private --model-gateway apim --force`; every later fix
went into the catalog and was regenerated, never edited in the generated repo.

- Provision 24 min (internal Container Apps environment 21 min); re-provisions
  9-10 min. APIM public network access stayed Disabled after each run.
- `azd deploy` from the operator host: remote ACR build, private image pull,
  hosted agent active in about 4 min.
- Killer prompts K1-K3 from inside the VNet: correct recommendations with the
  expected rules (BR-001/BR-005, BR-003 supervisor review, BR-004 missing
  photos), MCP tools over the internal environment, every model call through
  APIM (17 requests, all 200, in the APIM metrics).
- Foundry evaluation from inside the VNet: 18 rows, business-rules rubric
  18/18 (mean 4.11, threshold 4), coherence 18/18, task adherence and intent
  resolution 17/18; package gate COMPLETE.
- After rebasing on 2.43.0 (least-privilege agent identity), the gateway was
  deleted and the same environment re-proven on the direct private-endpoint
  route: K1-K3 correct, package gate COMPLETE. Its first evaluation scored 3.72
  (two citation rows judged 1, both answered without errors), the re-run 4.06.
- From the laptop: Foundry 403 "Public access is disabled", APIM refused the
  public client, MCP host has no public DNS. Safe-check private-network check:
  6 resources OK with the gateway, 5 after deleting it; remaining gaps were the
  design's deferred AI Search and Storage.

**Not proven:** egress allow-listing (NAT gateway without a firewall), a
non-Azure gateway, the Developer-tier gateway, custom DNS or hub-spoke peering,
Key Vault/Storage/AI Search/Cosmos private endpoints (checked by safe-check, not
generated), DR, budgets, Defender. **Telemetry gap:** hosted-agent log records
reached App Insights through the private link scope and carry each invocation's
trace id, but `invoke_agent` request spans were not observed, and the agent
process also tried to export to a second ingestion host
(`westus-0.in.applicationinsights.azure.com`) that doesn't resolve under the
private-only scope. Not diagnosed.
